## Interpretation
The fixed/random path through `SFT_vtc.sh` works end to end; the launcher is validated for those methods.
DRIP cause: `calc_loss` passes the sum of *relaxed* (soft) boundaries, a real number, to `Binomial.log_prob`, and torch's
default distribution argument validation (`__debug__` = True) rejects non-integers. This is independent of the ratio:
a CPU check in torch 2.10 rejects 648.3 under Binomial(1296, 0.5) the same way, so the 2x DRIP row (identical command in
Yusen's `SFT.sh`) can only have trained with validation off in Yusen's env (unverified how: env not readable from this
account). With validation off, `log_prob` evaluates the lgamma-based formula at the real value, a smooth relaxation,
which is what the 2x run optimised. Fix lives in the launcher (compressors/ is frozen): DRIP runs `train.py` through a
`python -c` wrapper that calls `torch.distributions.Distribution.set_default_validate_args(False)`; tested locally with
torchrun (argv, `__file__`, `__name__` preserved; log_prob returns -52.5 instead of raising).
Walltime: 488 x 87.5 s = 11.9 h of steps + ~6 min load per segment -> 3 x 4 h segments are not enough with the
up-to-14-min loss at each boundary; chains get 4 segments (the 4th exits immediately if the run finished).
